vérifiée en deux passes). Seuls 105 des 171 appels existent côté web, 38 côté mobile.

| Domaine | Routes sans interface |

| **Notifications** | `POST /notifications/broadcast` : le Super Admin ne peut pas envoyer de notification ciblée ni de maintenance. La page `/notifications` n'affiche que les siennes. |

## 4. Défauts constatés

1. `backend` : `npm run start:prod` lance `node dist/main` alors que le fichier compilé est
   `dist/src/main.js`. Le script est cassé.
2. **Accents absents** dans presque tous les libellés, web et mobile (« Republique »,
   « Decaissements », « Accedez a votre espace »).
3. **Mobile** : 3 tableaux dédiés (Ambassadeur, Chef d'orphelinat, Bailleur et Partenaire).
   Les 9 autres rôles reçoivent un tableau générique. Aucun écran Finance, Modération ni
   administration.
4. Super Admin : « Connectés maintenant » affichait 0 alors que des sessions étaient
   ouvertes. À vérifier : la présence en temps réel ne paraît pas alimentée.
5. Responsable National : « Régions couvertes 26 » compte toutes les provinces, pas celles
   qui ont un chef régional.
6. Mobile : « Décaissements à confirmer » est tronqué dans la carte.
7. Données de test dupliquées par les anciens scripts de bout en bout (4 projets
   « Rénovation du dortoir » identiques, 4 enfants « Testimoni »). Prévoir un script de
   remise à zéro du seed.
8. Premier démarrage de Metro sur cette machine : 165 s de compilation, et Expo Go est
   resté bloqué tant que le cache n'était pas vidé.

## 5. Limites de ce test

- **Émulateur** : seul l'Ambassadeur a été exercé sur Pixel_7. La saisie clavier par adb
  est trop lente ici (lettres doublées), j'ai arrêté les connexions suivantes. Le mobile
  des autres rôles reste à vérifier à la main.
- **iOS** : non testable sur Windows.
- **Web** : les pages de navigation de chaque rôle n'ont pas été balayées une à une, mon
  détecteur automatique donnait des faux positifs. Seuls les tableaux de bord sont
  vérifiés.
- Le rendu de l'émulateur est noir ou figé avec `-gpu auto`. `-gpu swiftshader_indirect`
  fonctionne.

## 8. Activation par code OTP envoyé par e-mail

Les identifiants SMTP (Gmail, port 587) sont dans `backend/.env`. Connexion et authentification
vérifiées. Un e-mail réel de test est parti vers un sous-alias de la boîte d'envoi.

- **Invitation** : code à 6 chiffres envoyé par e-mail avec le lien. Valable 15 minutes, 5 essais,
  renvoi limité à une fois par minute. Stocké haché, jamais renvoyé par l'API.
- **Inscription bailleur** : le compte reste inactif jusqu'à la saisie du code. Connexion refusée
  d'ici là avec un message explicite.
- **Routes ajoutées** : `POST /auth/activate/resend-otp`, `/auth/verify-email`,
  `/auth/verify-email/resend`. La route `POST /auth/activate` exige maintenant `otp`.
- **Web** : champ de code et « Renvoyer le code » sur `/activate`, étape de confirmation sur
  `/inscription`, bouton « Renvoyer le code » dans la liste des utilisateurs invités.
- **Testé** : sans code, code non numérique, 5 mauvais codes puis blocage, renvoi refusé avant
  60 s et accepté ensuite, code expiré, activation réussie, lien non réutilisable, connexion
  ensuite, inscription bailleur puis vérification, renvoi neutre pour une adresse inconnue.
  Activation vérifiée aussi dans l'interface web (mauvais code refusé avec compteur, bon code
  accepté, redirection vers le tableau de bord).
- **Mode test** : `MAIL_ECHO_OTP=true` n'envoie aucun e-mail et renvoie le code (ignoré en
  production). Le test `run-e2e-7.js` exige ce mode. Rappel : `APP_WEB_URL` doit être une adresse
  publique en production, sinon le lien du mail pointe vers `localhost`.
